* Follow runs through their summaries

See how the last runs of a site went, find the lines that failed and their logs, and have each run post its summary to a webhook.

** Before you start

- A site file whose =[filesystems] log_root= holds the run directories, where each run writes =summary.json= and =summary.html=.
- jq, for step 3.
- For steps 4 and 5, curl on the =PATH= of the build account, and an =http://= or =https://= URL that takes a JSON POST; for step 5, Python 3.

The output on this page comes from =docs/examples/summary.sh=, which runs both targets of a copy of the site file of [[file:build-from-ci.org][Build a list on every target from continuous integration]] with the =local= scheduler, its paths under =$WORK= and the stand-in =eb= of the [[file:../tutorials/first-build-list.org][tutorial]], which fails the lines whose easyconfig starts with =Broken-=.

** Steps

1. After a run, open the summary in its run directory, which the run names at its end:

   #+begin_example
   INFO [summary] zen2: summary.json and summary.html written in $WORK/site/logs/20261117_090000
   #+end_example

   =summary.html= needs no script and no network, and links each log relative to the run directory, so a copy of the directory, or a web server over the log root, shows the same page.

2. List the last runs, newest first:

   #+begin_src bash
   eb-pipeline status --site site.toml --last 2
   #+end_src

   #+begin_example
   20261117_120000  failed (exit 1)  $WORK/site/logs/20261117_120000/summary.html
     zen2  run  failed   exit 1          0.0 s  1 failed, 1 success; build failed
   20261117_110000  failed (exit 1)  $WORK/site/logs/20261117_110000/summary.html
     zen2  run  failed   exit 1          0.0 s  1 failed, 1 success; build failed
     zen4  run  success  exit 0          0.0 s  1 success
   #+end_example

   Each run is a line with its status, its exit status and its page, then a line for each target with its command, status, exit status and duration, the number of packages with each status, and the phases that came to neither =ok= nor =not configured=.
   The command is =watch= for a rebuild that [[file:rebuild-when-eessi-changes.org][Rebuild what an EESSI change reaches]] sets up.
   Without =--last=, =status= lists 10 runs; =--target zen4= keeps the runs of one target, and =--format json= prints their summaries.

   To focus on runs that need attention:

   #+begin_src bash
   eb-pipeline status --site site.toml --problems-only --last 5
   #+end_src

   This view includes failed runs and runs without a readable =summary.json=.
   =--last= counts matching runs, so newer successful runs do not hide an older failure.

3. List the lines of a run that did not succeed, with their logs, from its =summary.json=:

   #+begin_src bash
   jq -r '.targets[] | .name as $t | .packages[] | select(.status != "success") | "\($t)  \(.easyconfig)  \(.status)  \(.log)"' site/logs/20261117_120000/summary.json
   #+end_src

   #+begin_example
   zen2  Broken-1.0-GCCcore-15.2.0.eb  failed  $WORK/site/logs/20261117_120000/zen2/Broken-1.0-GCCcore-15.2.0.stdout.log
   #+end_example

4. To have each run post its summary, add a =[notify]= table that names the variable holding the URL of the webhook, which keeps the URL out of the site file:

   #+begin_src bash
   sed -n "/^\[notify\]/,\$p" notify.toml
   #+end_src

   #+begin_example
   [notify]
   webhook_env = "SUMMARY_WEBHOOK"
   when = "problems"
   #+end_example

   =when = "problems"= posts only after a run that did not exit 0; without it, every run posts.
   Check the site file:

   #+begin_src bash
   eb-pipeline check --site notify.toml
   #+end_src

   #+begin_example
   INFO [check] example: site file is valid
   #+end_example

   Then set the variable where eb-pipeline runs, as in the crontab or the CI job that starts it.

5. Before the real webhook, try the table against a listener on the build host.
   =listen.py= takes one POST on =127.0.0.1:8765=, prints what it got, and exits:

   #+INCLUDE: "follow-runs/listen.py" src python

   Start it, and then a run with its URL in the variable:

   #+begin_src bash
   python3 listen.py >listen.log &
   SUMMARY_WEBHOOK=http://127.0.0.1:8765/hook/XXXX eb-pipeline run --site notify.toml --list build.list --target zen2 --build-type production --log-stamp 20261117_130000; echo "exit $?"
   #+end_src

   #+begin_example
   ...
   ERROR [build] zen2: Broken-1.0-GCCcore-15.2.0: failed (exit 1)
   INFO [summary] zen2: summary.json and summary.html written in $WORK/site/logs/20261117_130000
   INFO [notify] zen2: summary.json posted to http://127.0.0.1:8765/...
   exit 1
   #+end_example

   The run exits 1, as a line failed, so =when = "problems"= posts its summary, and the listener got it:

   #+begin_src bash
   cat listen.log
   #+end_src

   #+begin_example
   listening on http://127.0.0.1:8765
   POST /hook/XXXX application/json: summary of run 20261117_130000, failed
   #+end_example

   eb-pipeline names only the scheme and the host of the URL, and hands curl the URL on its standard input, so that its path and its query show in no log and no process list.

** Check that it worked

With the URL of the webhook in the variable, a run that did not exit 0 ends with a line that names the scheme and the host of the URL, and a run that exited 0 sends nothing.
Here a stand-in for curl takes the POST to =https://hooks.example.org/build/XXXX=:

#+begin_src bash
export SUMMARY_WEBHOOK=https://hooks.example.org/build/XXXX
eb-pipeline run --site notify.toml --list build.list --target zen2 --build-type production --log-stamp 20261117_110000; echo "exit $?"
eb-pipeline run --site notify.toml --list example.list --target zen4 --build-type production --log-stamp 20261117_110000; echo "exit $?"
#+end_src

#+begin_example
...
INFO [summary] zen2: summary.json and summary.html written in $WORK/site/logs/20261117_110000
INFO [notify] zen2: summary.json posted to https://hooks.example.org/...
exit 1
...
INFO [summary] zen4: summary.json and summary.html written in $WORK/site/logs/20261117_110000
INFO [notify] zen4: the run exited 0 and notify.when is problems; nothing sent
exit 0
#+end_example

The webhook gets the =summary.json= of the run directory as it is when the target's run ends, with every target that has written to it by then.

A scraper that reads Prometheus text takes one result file:

#+begin_src bash
eb-pipeline metrics --result result.json
eb-pipeline metrics --result result.json --format json
#+end_src

The text names the site, the target, the build type, the run id and whether the run was sharded, and gives the exit code, the line counts and each phase.
=--format json= prints the same facts as one document whose =kind= is =status=.
Either command exits 0 when the file can be read, including when the run failed.

** Extract a retry list from an unfinished run

When a run stops with failed, refused, pending or skipped lines, =eb-retry-list= reads the original build list (or easystack) and either =result.json= or =summary.json= and writes only the unfinished lines in their original order with their =eb= options:

#+begin_src bash
eb-retry-list --summary site/logs/20261117_120000/summary.json --target zen2 --list build.list --out retry.list
if [ -s retry.list ]; then
    eb-pipeline run --site site.toml --list retry.list --target zen2 --build-type production
fi
#+end_src

Lines recorded as =success= and lines deselected by =[targets.select]= are left out, so =--rebuild= lines that already succeeded are not rebuilt.
Keep =retry.list= separate from the result, summary and build list.
=eb-retry-list= refuses an =--out= path that aliases one of those inputs through a symbolic or hard link, before it writes the output.
Use =--result result.json= in place of =--summary= and =--target=, and =--status failed= to narrow to specific line statuses.
When the build-list path recorded in the result or selected target is still readable, reuse it instead of naming it again:

#+begin_src bash
eb-retry-list --result result.json --recorded-list --out retry.list
#+end_src

The recorded path is used as written.
Keep =--list= when the list moved or when you run the command from another working directory.

To branch on the command status instead of inspecting the output file, add =--require-lines=:

#+begin_src bash
if eb-retry-list --result result.json --recorded-list \
     --out retry.list --require-lines; then
    eb-pipeline run --site site.toml --list retry.list \
      --target zen2 --build-type production
fi
#+end_src

The option exits 1 after writing an empty retry list and exits 0 after writing one or more lines.
Input and processing errors still exit 2.

To retry only failures that =eb-stack= identifies as transient, add =--classify=:

#+begin_src bash
eb-retry-list --result result.json --list build.list --classify --out retry.list
#+end_src

This starts =eb-stack stack bot-classify --json= once for each unfinished line's recorded log and keeps only =interrupted=, =resource= and =timeout=.
Install =eb-stack= on =PATH= before using the option.
If a line has no recorded log, =eb-stack= is missing or fails, or its output cannot be read, =eb-retry-list= exits 2 and writes no retry list instead of treating every line as retryable.

=--class= names the classes to keep instead of those three.
A class is the =class= or =sub_class= string in that JSON, such as =timeout= or =source=.
=--class= needs =--classify=, and it replaces the default rather than adding to it:

#+begin_src bash
eb-retry-list --result result.json --list build.list --classify --class source,checksum --out retry.list
#+end_src

To see which of the remaining lines =eb-stack= predicts will not fit a node, add =--node=.
The value is =CORES:MEMORY_MIB= or =CORES:MEMORY_MIB:TARGET=.
=eb-retry-list= writes those lines to a temporary easystack and starts =eb-stack stack oom --node NODE --easystack= on that file.
Each warning is printed on stderr.
The lines stay in the retry list unless you also pass =--drop-oom=:

#+begin_src bash
eb-retry-list --result result.json --list build.list --classify \
  --node 32:65536:x86_64/amd/zen4 --drop-oom --out retry.list
#+end_src

=--arch= and =--easyconfigs= are passed through to the same =stack oom= command when you set them.
=--node=, =--drop-oom=, =--arch= and =--easyconfigs= need =--classify=, and =--drop-oom=, =--arch= and =--easyconfigs= need =--node=.
=eb-retry-list= does not classify a log or estimate memory itself.
With no lines left after classification, =stack oom= is not started.

** If it fails

| Message                                                                                                                      | Cause                                                                                                          | What to do                                                                           |
|------------------------------------------------------------------------------------------------------------------------------+----------------------------------------------------------------------------------------------------------------+--------------------------------------------------------------------------------------|
| =INFO [status] -: no runs under LOG_ROOT=                                                                                    | No run has written under the =log_root= of the site file: none has run yet, or the runs use another site file. | Give =status= the site file that the runs use.                                       |
| =RUN  no summary.json: the run is still going, or ended before writing one=                                                  | The run has not ended, or it stopped before it wrote its summary.                                              | Wait for the run to end, or read the logs in its run directory.                      |
| =WARN [summary] TARGET: no summary written: PATH: ERROR=                                                                     | The run could not write its summary.                                                                           | Fix what =ERROR= names, such as the permissions or the free space of the log root.   |
| =WARN [notify] TARGET: SUMMARY_WEBHOOK is unset or empty; nothing sent=                                                      | The variable that =webhook_env= names is not set where eb-pipeline runs.                                       | Set it there, as step 4 says.                                                        |
| =WARN [notify] TARGET: the URL in SUMMARY_WEBHOOK must start with http:// or https://; nothing sent=                         | The variable holds something other than a URL with its scheme.                                                 | Put the URL of the webhook in it, with =https://= or =http://=.                      |
| =WARN [notify] TARGET: POST of summary.json to URL failed: curl exited 7: ERROR=                                             | Nothing took the connection at the host and port of the URL.                                                   | Check the URL, and that the service of the webhook, or the listener of step 5, runs. |
| =WARN [notify] TARGET: POST of summary.json to URL failed: curl exited 22: curl: (22) The requested URL returned error: 500= | The webhook answered with an HTTP error.                                                                       | Read what its service logged for the POST.                                           |

A summary that is not written or not sent leaves the exit status of the run as it was.
